## 1. 第一原则：不假定用户需要改变

系统必须先帮助用户走完这四步，才允许进入正式训练：

```text
为什么可能需要改变
↓
为什么改变很难
↓
我到底有没有必要改变
↓
我是否自主决定改变
```

**产品级判据（不是愿望，是可测的）：新用户不能在没有经过 AWARE → UNDERSTAND → DECIDE 的情况下，
被系统推进到「我要改变」。** 服务层与界面两层各有一道强制：`canEnter(…, 3)` 要 `gate.commit`，
创建入口要 `gate.readiness`。

---

## 2. 八个阶段（固定，一次只推进一个 Active Change）

| # | 阶段 | 它要回答的问题 |
| --- | --- | --- |
| 00 | AWARE | 我是否真的存在值得改变的问题？ |
| 01 | UNDERSTAND | 为什么"知道"不等于"做到"？为什么改变困难？ |
| 02 | DECIDE | 这个改变是否真的有必要、是否值得？ |
| 03 | REBOOT | 明确真正想改变的方向，并形成最小可执行实验。 |
| 04 | TRAIN | 现实行动、记录事实、形成训练循环。 |
| 05 | ADAPT | 中断 → 分析阻碍 → 调整 → 恢复 → 学习。 |
| 06 | INTERNALIZE | 逐步降低提醒、监督和系统依赖。 |
| 07 | GRADUATE | 能够在没有 OpenReboot 的情况下继续。 |

阶段只能一级一级往前走；跳步被 `gate.skip` 拒。

---

## 3. DECIDE 的三个合法出口

| 出口 | 含义 | 之后会发生什么 |
| --- | --- | --- |
| `change`（我决定改变） | 自主决定进入训练 | 才允许进 03 REBOOT |
| `observe`（还没想清楚，继续观察） | 暂时不确定 | 这条判断留在本机，用户可回来重选 |
| `keep`（想清楚了，暂时不改变） | 理解收益与代价后，决定暂不改变 | 同上，是结论，不是退出系统 |

两条硬规矩：

1. `observe` / `keep` **不自动归档**。旧实现一选就把这条 Change 关成 closed，等于把「继续观察」做成死路
   —— 用户既回不到自己的判断，也看不见当初的理由。现在必须**由用户自己按「归档」**，
   归档之后才让出那唯一的一个 Active Change 名额。
2. 已经选了 `change` 的那条不许被归档（归档只服务另外两个出口），防止训练中途被误关。

内部字段名与本文的出口名一一对应：`DecisionKind = "change" | "observe" | "keep"`（真源在
`src/domain/types.ts`，本文不重复定义常量）。v0.1.0 发布过的旧导出文件里的
`commit / notNow / stayAsIs` 由导入层显式翻译；认不出的值整份拒绝，不静默收下。

## 4. 其余不变量（这些是判据，不是风格）

- **一次只有一个 Active Change**（§3 原方案，继续有效）。
- **Missed ≠ 终止**：没做到只开一条"中断"，走 Diagnose → Intervention → Recovery → Learn。
- **行为比宣言重要**：`declaredIntent` 与 `evidenceBasedTarget` 分开记；样本不足时不许算"言行差距"。
- **系统主动减少对自己的依赖**：监督等级只降不升，降级要证据，毕业要用户自己确认。
- **不做**医疗、心理治疗、诊断；不做AI 人格判断。
- **用户数据默认只在本机浏览器**（IndexedDB），可导出 / 导入 / 清空。

---

## 5. v0.1 明确不做（下一版再谈）

云端 AI、用户账号、云同步、社交、排行榜、连续打卡、积分、付费、后端数据库、多人监督、
大规模 Protocol Marketplace。

## 6. 线上演示的边界

GitHub Pages 提供的是**同一份静态代码**的在线体验：无账号、无后端、无遥测、无第三方分析。
但托管平台（GitHub）可能按它自己的政策处理正常访问日志 —— 这与"OpenReboot 收集你的训练数据"
是两件事，表述时必须分开写，不许为了好听合并成"没有服务器"。
